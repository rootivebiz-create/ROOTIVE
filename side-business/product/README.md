# しめ日ラボ（製品）— お客様に納める「月末の締め」の仕組み

業務委託ドライバーに支払う会社（5〜50 人ほど）の、月末の締めをまとめて引き受ける Web アプリです。
**お客様 1 社ごとに、お客様の Vercel ＋ Postgres に置きます**（データはお客様のもの）。全部の表に `tenant_id` があるので、将来は 1 つにまとめて提供（SaaS）にも切り替えられます。

- 何を・なぜ・どこまで：[`SPEC.md`](SPEC.md)（需要の証拠・既存との違い・デモの台本・受け入れ条件・言ってはいけないこと）
- 作りの決まり：[`ARCHITECTURE.md`](ARCHITECTURE.md)（機能を足す人向け）

## できること（画面）

| 画面 | 中身 |
|---|---|
| 今月の締め（ホーム） | 取り込み → 見張り番 → 明細 → 締め → 振込 の進み具合と「次にやること」（振込データは締めてから作る）。見つけたお金・未解決の質問 |
| 取り込み `/import` | 今の Excel・CSV をそのまま置く。列の意味を当て、形を覚える（翌月から 1 クリック）。名前の表記ゆれを覚える。ファイルの合計と照合。取り消しできる |
| 稼働と調整 `/work` | 月の稼働（ドライバー × 案件）の手直しと、その月だけの足し引き |
| 見張り番 `/watch` | 締める前に、記録から分かることを赤・黄で（取引条件の明示・60 日・合意の無い控除・振込手数料・経過措置・口座なし・急な増減 など）。根拠と出典つき。**判定はしない** |
| 取引条件の明示 `/terms` | 台帳から明示書を作り、ドライバーへリンクで渡して「受け取りました」を残す |
| 支払明細 `/statements` | 仕入明細書の記載事項を載せた明細と PDF。ドライバーへ署名つきリンク（ログイン不要）。「確認しました」・行ごとの質問・版の履歴 |
| 明細の検索 `/records` | 月をまたいで、期間・振込額の範囲・ドライバーで明細を探す。前の版も開ける。索引は CSV（明細の画面の「過去の明細を探す」から） |
| 締め `/close` | 月を締める（DB でも書き換えを止める）。オーナーだけが理由つきで外せる。操作の記録 |
| 振込データ `/transfer` | 全銀の総合振込データ（振込はお客様が行う。締めたあとに作ると金額が変わらない）。実際に振り込んだ日の記録 |
| Excel と比べる `/parallel` | 今の Excel の振込額と並べて、差と原因の候補を出す（並行運用）。全員が一致か説明済みになったら本番へ |
| 元請との突合 `/reconcile` | 元請の支払通知を置くと、自社の記録と比べて差を金額で。丁寧な問い合わせ文の下書き。3 か月のレポート。営業所ごとなど同じ月に何通も届くときは「足す」で合計して比べる。PDF しか無いときは表を貼り付ける（読み取った結果は人が確かめる） |
| 利益 `/profit` | 案件・元請・ドライバー別の利益と推移、経過措置の負担、社長の 1 枚（PDF） |
| 会計ソフトへ `/export` | 弥生会計のインポート形式（既定）・マネーフォワードの仕訳帳・汎用 CSV（**取り込む前に税理士さんと勘定科目・税区分を確かめる**） |
| 設定 `/settings` | 会社・ドライバー・元請・案件・人ごとの単価・控除のルール・利用者・自分のパスワード・ヘルプ |

役割：オーナー（すべて・利用者の管理・締めの解除）／事務（登録・取り込み・明細・振込・締め）／閲覧（見るだけ）。ドライバーはログインしない（リンクだけ）。

## お客様 1 社を立ち上げる（1〜2 時間）

### 1. お客様に用意してもらうもの
- **Vercel のアカウント**（商用なので **Pro プラン**。無料の Hobby は商用で使えません）。こちらを「メンバー」に招待してもらうか、Vercel のトークンを発行してもらう
- **Postgres**：Supabase か Neon（どちらも東京リージョンあり）。接続文字列（`postgres://…`）をもらう。**バックアップ（日次）が有効か**を確かめる
  - **DB のプランの確かめ（お客様の本番）**：
    - 無料のプランは使わない。しばらく使わないと止まる（Supabase の無料は 1 週間ほどで一時停止し、月末に開くと動かない）・日次のバックアップが無い・容量が小さい
    - 有料のプラン（例：Supabase Pro・Neon の有料）で、**日次のバックアップ（できれば日時を指定して戻せるもの）** が入っていること
    - リージョンは東京（`ap-northeast-1`）。接続文字列はプールの方（Supabase は Transaction pooler・Neon は `-pooler`）を使う
    - 月に 1 回、しめ日ラボの「データの書き出し」（`/data`）の ZIP をお客様の手元にも残してもらう（DB の外の控え）
- 請求はお客様のアカウントに直接かかります（当方は立て替えない）

### 2. 置き場所を作る（1 回のコマンド）
製品のコードは **オーナー個人の GitHub リポジトリ** に置いてある前提です（`side-business` を個人のリポジトリへ移す手順はサイトの README）。

```bash
cd product
DATABASE_URL='postgres://…（お客様の DB）' VERCEL_TOKEN='…' \
  npx tsx scripts/provision.ts --client "Sample Unso" --repo 自分のアカウント/shimebi --root product [--team team_xxx] \
    [--support-email 自分の問い合わせ用のメール] [--support-line https://lin.ee/…]
```

これで ① DB にマイグレーション ② Vercel にプロジェクト（リポジトリとつなぐ）③ 環境変数（`DATABASE_URL`・`APP_SECRET`・`SETUP_TOKEN`）④ 本番のデプロイ ⑤ **最初のオーナーの登録リンク**（`/setup?token=…`）の表示 までを行います。先に `--dry-run` で中身を確かめられます。

- **お客様の DB と秘密の値は、本番（Production）のデプロイにだけ入れます**。Vercel は本番のブランチ以外への push ごとにプレビューを作るので、プレビューには別の `APP_SECRET`・`PGLITE_DIR=memory`・`DEMO_MODE=1` だけを入れ、揮発する架空の会社（デモ）として開けるようにしています。ビルドの前のマイグレーション（`vercel-build`）も、`VERCEL_ENV` が `production` のときだけ当てます（プレビューのビルドでお客様の DB を変えない）
- **この形にする前に作ったプロジェクト**（`DATABASE_URL` などがプレビューにも入っているもの）は、一度だけ Vercel のプロジェクトの Settings → Environment Variables で直してください：
  1. `DATABASE_URL`・`APP_SECRET`・`SETUP_TOKEN`（デモなら `DEMO_MODE`）の「Preview」のチェックを外す（Production だけにする）
  2. Preview だけに `APP_SECRET`（新しく作った 32 文字以上のランダムな値。本番と同じにしない）・`PGLITE_DIR=memory`・`DEMO_MODE=1` を足す
  3. 直すまでのあいだも、`scripts/migrate.ts` はプレビューのビルドではマイグレーションを当てません（この版のコードが入ったブランチから効きます）

- 秘密の値はコマンドの引数に書かず、環境変数で渡します（履歴に残さない）
- `--support-email`・`--support-line` を付けると、ヘルプの画面に問い合わせ先が出ます（付けないと「導入を担当した者にご連絡ください」と出ます。あとから Vercel の環境変数で足しても同じ）
- 画面から置けるファイルは **4MB まで**（Vercel は画面からの送信を 1 回 約 4.5MB までに制限しているため）。大きい Excel は、使っていないシートや画像を消すか CSV にしてもらう。全データの読み戻しで 4MB を超える ZIP は、手元から `scripts/restore-tenant.ts` で読み戻す
- Vercel のプロジェクト設定で **「Include source files outside of the Root Directory」が有効** になっていることを確かめてください（計算の部品を `../lib` から読むため。新しいプロジェクトでは既定で有効）
- Vercel は `product/` にだけ `npm install` します（`side-business/node_modules` は作られない）。共有の部品（`../lib`・`../components/ui.tsx`）が読む `react` の型は、`tsconfig.json` の `paths` で `product/node_modules` から読みます。共有の部品には react のほかに npm のパッケージを読ませないこと（`tests/standalone-build.test.ts` が確かめます）
- **最初のお客様の前に、デモを一度 Vercel に実際にデプロイして、ビルドが通ることを確かめてください**（手元では `side-business/node_modules` があるので、ここでしか分からない失敗があります）
- 以降の本番のデプロイでは、ビルドの前に `vercel-build`（`scripts/migrate.ts --if-configured`）が **マイグレーションを自動で当てます**（プレビューのビルドでは当てません）

### 3. お客様と最初の午後（一緒に画面を見ながら）
1. 登録リンクをお客様の社長だけに渡し、オーナーとして登録してもらう
   - 続けて「設定 → 利用者」で、**もう 1 人（役員・事務の責任者など）をオーナーとして招待してもらう**。オーナーが 1 人だけだと、その人がパスワードを忘れたときに社内で招待を作り直せる人がいない（画面にも「オーナーが 1 人だけです」と出ます）
2. 「最初の設定」（ホームの帯から）：会社の基本 → 先月の Excel（知らない名前・案件はその場で登録、控除の提案も）→ ドライバー・元請と案件・控除のルールの確かめ（取り込みで入っていれば済み）→ Excel と比べる → 取引条件の明示。マスタを先に埋めさせない（SPEC P0-1）
3. 先月分で明細を作り、今の Excel の振込額と比べる（並行運用）。差があれば原因の候補を一緒に見て、ルールを直す
   - **報酬の決め方を先に聞く**：今の計算は「支払単価 × 数量」（人ごとの単価は取り込みの単価の列から登録できる）と、控除・その月の調整まで。**段階制・最低保証・日額＋歩合** は計算できないので、その会社はお試しの前に範囲を決める（差は毎月の調整で入れることになる）
   - 実物の Excel で、読めない形が無いかを確かめる（1 人 1 枚の表・人が横に並ぶ表・○×の表・燃料や立替の列は読める。ほかの形はお試しで確かめてから約束する）
   - 元請の支払通知の形も聞く：CSV・Excel か PDF か、営業所ごとに何通も届くか。何通も届くときは「足す」で 1 か月分にまとめて比べる（形がまったく違う営業所は、元請を営業所ごとに分けて登録する）。PDF しか無いときは表の貼り付けで受ける（列がずれることがあるので、読み取った品目と金額を一緒に確かめる）
4. 2 か月続けて全員が一致（か説明済み）になったら「本番に切り替える」

### 4. 毎月の保守（月額に含むもの）
- **エラーの見方**：画面で「保存できませんでした」などが出たときの中身は、Vercel のプロジェクトの Logs（Functions）に 1 行の JSON（`"event":"action failed"`・エラーの文・DB のエラーの番号・どこで起きたか）として出ます。入力の値は出しません。お客様ごとに Log Drain（外のログの置き場所）をつなぐか、月に 1 回 Logs を `action failed` で探す
- 製品を直したら個人のリポジトリへ push → 各お客様の Vercel が自動でデプロイ（マイグレーションも自動）
  - **お客様へ出す版は `release` ブランチ** にしておくと安全です（Vercel の Production Branch を `release` に）。`main` で確かめてから `release` へ
- 制度の変更（経過措置の段・源泉の率）は `../lib/payroll/tax.ts`・`../lib/engine/withholding.ts` の表を直すだけで全社に効きます
- 銀行の休みの日（明細の振込予定日・振込データの指定日・60 日の確かめ）に使う祝日の表は `../lib/tools/jp-holidays.ts`（2030 年まで）。毎年 2 月に翌年の春分の日・秋分の日が官報で決まったら、内閣府の一覧と照らし合わせる
- お客様がやめるとき：オーナーが「データの書き出し」（`/data`）で全データを ZIP で持ち帰れます

### 5. 入れなくなったとき（オーナーがパスワードを忘れた・オーナーがやめた）
ふだんのパスワード忘れは、社内のオーナーが「設定 → 利用者」で招待を作り直せば済みます（ヘルプの「パスワードを変えたい・忘れた」）。
**オーナーが 1 人だけで、その人が入れない**ときは、画面の中で直せる人がいないので、こちらで入り直しのリンクを作ります（ヘルプの連絡先に来る相談）。

1. **ご本人かを確かめる**：登録してあるメールアドレスと、会社の代表の電話番号へ折り返すなど、ふだんの連絡先で確かめる（メールだけで受けない）
2. 利用者の一覧を見る（お客様の DB の接続文字列は、お客様の Vercel の環境変数 `DATABASE_URL` と同じもの。コマンドの引数に書かない）：
   ```bash
   cd product
   DATABASE_URL='postgres://…（お客様の DB）' npx tsx scripts/reset-access.ts --list
   ```
3. その人の入り直しのリンクを作る（先に `--dry-run` で相手を確かめられます）：
   ```bash
   DATABASE_URL='postgres://…' npx tsx scripts/reset-access.ts --email 社長のメール --url https://お客様のURL
   ```
   - リンクは **1 回だけ・24 時間**（`--hours` で 168 時間まで）。画面の招待と同じ `/invite/…` で、開いて新しいパスワードを決めると入れます。前のパスワードは使えなくなり、止めてあった人は再開になります
   - リンクは画面に 1 度しか出ません（DB にはハッシュだけ）。**ご本人にだけ** 渡す（グループの LINE・転送されるメールに貼らない）
   - 同じ人への古い招待は使えなくなります。操作の記録に「利用者を招待した」（`detail.via = "reset-access"`、やった人は「自動」）が残ります
   - **オーナーがやめてしまった**ときは、社長が決めた後任（すでに利用者の人）に `--make-owner` を付けて作る（受け取るとオーナーになる）。やめた人は、入れたあとに画面で「止める」
   - 端末をなくした・のぞかれたおそれがあるときは `--sign-out` で、その人のいまのログインをすべて切る
   - 同じメールアドレスが複数の会社にあるとき（まとめて提供に移ったあと）は `--tenant 会社の id`
4. 入れたら、もう 1 人をオーナーにしてもらう（上の「最初の午後」の 1.）

- 全データを別の置き場所へ読み戻したあとも、パスワードは書き出しに入っていないので、同じ手順でオーナーのリンクを作ります
- 表（マイグレーション）は変えません。DB に書くのは、招待 1 件・古い招待の期限・（`--sign-out` のとき）ログインの削除・操作の記録だけです
- ログインは、使わない日が 14 日続くと切れます（使っている間は延びます。ただしログインしてから 90 日たつと、使っていても一度切れます）。パスワードを思い出せないまま入れなくなることがあるので、上の 2 人目のオーナーを先に作っておくのがいちばんの備えです

## デモを公開する（商談とサイトの「デモを触る」）

デモは **来た人ごとに架空の会社を 1 つ作り、24 時間で消えます**（ほかの人の操作は見えない）。ログインは要りません。

1. **Neon か Supabase の無料の Postgres** を 1 つ作る（デモ専用。お客様のものと分ける）
2. オーナー自身の Vercel（Pro）で、同じリポジトリから別のプロジェクトを作る：
   ```bash
   DATABASE_URL='postgres://…（デモ用）' VERCEL_TOKEN='…' npx tsx scripts/provision.ts --demo --repo 自分のアカウント/shimebi --root product
   ```
   （環境変数に `DEMO_MODE=1` が入ります。`SETUP_TOKEN` は入りません）
3. 出てきた URL の `/demo/start` が入口です。サイトの環境変数 `NEXT_PUBLIC_PRODUCT_DEMO_URL` にこの URL を入れると、サイトの「製品のデモを触る」がここにつながります
   - 入口は **開いただけでは何も作りません**（「デモを始める」を押したときだけ架空の会社を作る）。検索のロボットやリンクのプレビュー（LINE・Slack など）が開いても、デモの会社は増えません。入口は検索に出さない設定です（`X-Robots-Tag`・`robots.txt`）
   - 使っている途中の人のデモは、24 時間たつまで消しません。デモの会社が 300 を超える・10 分で 60 を超えて作られる・DB が `DEMO_DB_LIMIT_MB`（既定 400MB）を超えるときは、「混み合っています」と出して新しく作りません

PGlite（DB なし）のままでは、サーバーが複数に分かれる Vercel ではデモの会社が消えることがあるので、**デモにも Postgres を使ってください**。

デモでは、無料の小さな DB をいっぱいにしないよう、置けるファイルを **1 件 1MB まで・1 つのデモの会社で 15 件（中身の合計 1MB）まで** にしています（`server/features/import/demo-budget.ts`）。上限に届いた人には「新しいデモを始めてください」と出ます。

## 環境変数

| 名前 | 必須 | 中身 |
|---|---|---|
| `DATABASE_URL` | 本番 ◯ | お客様の Postgres（`postgres://…`）。無ければ PGlite（手元・テスト用） |
| `APP_SECRET` | 本番 ◯ | 32 文字以上のランダムな値（ドライバーのリンクの署名。口座の目印・接続元の目印の鍵もここから作る）。**変えると発行済みのリンクがすべて使えなくなる**。また、次の振込データを作るときに **全員が一度「口座が変わった人」に出ます**（前の振込の口座の目印と比べられなくなるため。ご本人に確かめてから進める）。確認の記録の「接続元」の目印も、前の記録とは違う値になります。プレビューには本番と別の値を入れる |
| `SETUP_TOKEN` | 本番 ◯ | 最初のオーナーの登録（`/setup?token=`）の合言葉。登録が済めば `/setup` は開けなくなる |
| `DEMO_MODE` | デモだけ | `1` で来た人ごとの架空の会社（お客様のプロジェクトでも、プレビューには `1` を入れる） |
| `DEMO_DB_LIMIT_MB` | 任意 | デモの DB がこの大きさ（MB）を超えたら、新しいデモを作らない（既定 400） |
| `DEMO_READONLY` | 任意 | `1` でデモの保存を止める（ふだんは不要） |
| `PGLITE_DIR` | 任意 | 手元の PGlite の置き場所（`memory` で揮発。プレビューは `memory`） |
| `NEXT_PUBLIC_SUPPORT_EMAIL`・`NEXT_PUBLIC_SUPPORT_LINE_URL` | 任意 | ヘルプの画面に出す、問い合わせ先 |

## 開発する人向け

```bash
cd side-business && npm install        # 計算の部品（../lib）の型のため
cd product && npm install
npm run dev                            # http://localhost:3300（PGlite。最初は /setup で会社を作る）
DEMO_MODE=1 npm run dev                # デモ（/demo/start）
npm run check                          # 型・Lint・テスト・本番ビルド
npm run test:e2e                       # ブラウザでの確認（本番のビルドを作ってから next start -p 3310。320px・375px とパソコン。デモの架空の会社）
E2E_SKIP_BUILD=1 npm run test:e2e      # すぐ前に作ったビルドのまま、もう一度（ビルドを飛ばす）
E2E_DEV=1 npm run test:e2e             # 同じ確かめを開発用のサーバーで（ビルドしない。最初の表示が遅い）
npx tsx scripts/make-samples.ts        # 取り込みの見本ファイル（public/samples）を作り直す
npm run db:generate -- --name 名前     # 表を変えたらマイグレーションを作る（db/migrations）
```

- テストは PGlite（メモリの中の Postgres）で動くので、外の DB は要りません
- ブラウザでの確認（`e2e/`）は 5 つ。どれもデモの架空の会社（ドライバー 8 人・案件 5。最初の設定は済み）で動きます
  - `demo.spec.ts`：SPEC §3 の流れ（取り込みの見本 → この月をすべて入れ替えて反映 → 見張り番の赤 2 件をメモつきで確認済み → 明細 → リンクをコピー → ログインしていないブラウザで「内容を確認しました」→ 一覧が確認済み → 行からの質問で未読 1 → 明細の PDF の金額 → 振込データ（全銀 120 桁のファイル）→ 締め → 締めたあとも確認できる → 突合の見本で ¥91,700 → 問い合わせ文と PDF → 問い合わせ済み → Excel に戻す）。0:00 から「確認しました」までの会社の側の操作は **15 回**（上限 25 回を確かめる）。PDF の文字は `e2e/pdf-text.ts` で取り出して画面の数字と比べます
  - `layout.spec.ts`：320px・375px で 50 ほどの画面（設定・最初の設定の各段・ドライバーの /s と /t・使えないリンクの画面・デモの入口を含む）が横にはみ出さない（畳んだ所を開いても）・コンソールにエラーが無い・h1 がある・押せる所が 44px 以上
  - `security.spec.ts`：書き換えたドライバーのリンク・作り直す前のリンクは「このリンクは使えません」（404・`X-Robots-Tag: noindex`・`Cache-Control: no-store`・`Referrer-Policy: no-referrer`）、別のデモの会社の明細の PDF は 404、デモの入口の `next` に別のサイトを入れても外へ移らない
  - `mobile.spec.ts`（メニューの印・明細の検索・長いファイル名）と `month.spec.ts`（締め（断られても入力が残る）→ 振込データ → 締めを外す）
  - SPEC §3 の「空の会社から 4 つの質問」の台本そのものは、デモが最初から入った会社なので、まだ自動では確かめていません
  - デモの入口は同じ接続元から 10 分に 10 社までなので、テストは社ごとに別の接続元（`X-Forwarded-For`）として入ります（`e2e/helpers.ts` の `asNewVisitor`）
- 締めた月の稼働・調整・明細、明細の版、操作の記録は **DB の引き金でも** 書き換えを止めています（`db/migrations/0001`・`0003`・`0005`・`0006`・`0008`）

## 気をつけること
- 見張り番・明細・問い合わせ文は **「記録から分かること」と「確認をおすすめ」まで**。適法・違反・税務の結論は出しません（`SPEC.md` の「言ってはいけないこと」。テストでも確かめています）
- 会計ソフトの取り込みの形式・税区分の名前は **体験版で取り込めたことを確かめるまで「対応」と言わない**
- 取適法・フリーランス法の数字（しきい値・日数）は、法改正や公取委の資料で変わったら `server/features/watch/rules.ts` を直します
